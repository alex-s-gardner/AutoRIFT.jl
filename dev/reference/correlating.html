Correlating ​

autorift takes two images and returns a grid of sub-pixel displacements. The other names here reuse the plans, buffers and FFT workspace across many pairs of the same size.

FFTW plans are measured on first use and saved to a wisdom file. A process that finds the file starts at full speed; one that does not measures its plans first. On a workstation the file persists between processes. In a deployment that discards its filesystem between jobs, populate it ahead of the first job with AutoRIFT.precompute_fftw_wisdom; AutoRIFT.fftw_wisdom_path gives its location and how to redirect it.

AutoRIFT.AutoRIFT Module
julia
AutoRIFT

Fast dense image motion tracking by normalized cross-correlation. Two images of the same scene that differ by motion go in; a grid of sub-pixel displacements comes out.

julia
out = autorift(image1, image2; chip_size = 32, search_radius = 25)
out.dx, out.dy, out.correlation

Applications include glacier and ice-sheet velocity, sea-ice drift, particle image velocimetry, digital image correlation and strain mapping, cell and tissue motion, and video motion estimation.

The core operates on plain AbstractMatrix in pixel coordinates and knows nothing about coordinates or projections. Load Rasters or DimensionalData to accept dimensional arrays and receive a stack with coordinates, CRS and — given an acquisition interval — velocity attached; those methods live in package extensions, so the core stays cheap to load.

The algorithm descends from NASA JPL's autoRIFT and produces the ITS_LIVE velocity products, its largest deployment.

AutoRIFT.autorift Function
julia
autorift(reference, secondary; kwargs...)

Estimate the displacement of surface features between two images of the same scene, on a grid, to sub-pixel precision.

The input type determines the return type and the displacement convention:

inputreturnsdisplacement
MatrixAutoRIFT.MultichipResultdx, dy: pixel offset, dy down rows
AbstractDimArrayDimStackdx, dy: as above, with coordinates
AbstractRasterRasterStackvx, vy: feature motion, +vy north

Every form carries correlation (the peak similarity), peak_ratio, chip_size (the chip-size level that produced each estimate) and interpolated (values filled from neighbors rather than measured) per point.

The AbstractDimArray and AbstractRaster methods need DimensionalData or Rasters loaded. Only the raster path knows the map orientation, so only it reports vx/vy: it negates the correlator's secondary-to-reference offset to give feature motion and flips row-down to north-up. A north-up and a south-up raster of one scene give the same answer. Radar slant-range geometry has no CRS and takes the DimStack path.

See AutoRIFT.params for the full keyword list.

AutoRIFT.autorift! Function
julia
autorift!(cache)

Run the correlator on cache's current pair, reusing its buffers and FFT plans, and return the MultichipResult (also stored in cache.result).

For batch processing: AutoRIFT.init allocates and plans once, reinit! swaps in the next image pair, and autorift! reuses both. See AutoRIFT.Cache.

julia
cache = AutoRIFT.init(first_pair...)
for (a, b) in pairs
    reinit!(cache; reference = a, secondary = b)
    save(autorift!(cache))
end

CommonSolve.init Function
julia
AutoRIFT.init(reference, secondary; kwargs...) -> Cache

Prepare to correlate reference against secondary, allocating buffers and planning transforms once.

Accepts the same keywords as autorift. The images are preprocessed immediately, except under process_block_size, where each block is filtered from its own read window during the run and no whole-scene filtered copy is formed; AutoRIFT.imagepair then throws.

Use this with reinit! when processing many pairs, so the grid, output arrays and FFT plans are built once. For a single pair, call autorift.

AutoRIFT.reinit! Function
julia
reinit!(cache; reference, secondary, reference_valid, secondary_valid) -> cache

Point cache at a new image pair, reusing its grid, output arrays, and transform plans.

Throws DimensionMismatch unless the new images have the shape of the originals.

An omitted image keeps its current value, so reinit!(cache; secondary = next) advances one image of a time series while holding the other fixed. An omitted mask is kept only if its image was also omitted, and otherwise is re-derived from finiteness, since a mask describes particular pixels of one image.

For a whole-scene cache, only changed images are re-filtered, and an image already prepared in either slot is reused. Walking consecutive acquisitions, where each new reference is the previous secondary, filters each image once.

Params is not reinitialized

The cache keeps its Params. RotationSearch's about is a per-pair quantity, so a cache built with about = scene_rotation(guess) applies the first pair's rotation to every later pair. For a rotating time series, call autorift per pair with a freshly fitted about.

Returns the cache.

AutoRIFT.Cache Type
julia
Cache

Preallocated state for correlating many image pairs with the same configuration.

Holds the resolved parameters, the search grid and the output arrays. The FFT plans live in a process-wide plan cache. Built by AutoRIFT.init, advanced to the next pair by reinit!, and run by autorift!.

Not thread-safe: use one cache per task. Tasks may each hold their own and run concurrently; see autorift!.

AutoRIFT.autorift_with_grid Function
julia
AutoRIFT.autorift_with_grid(reference, secondary; kwargs...) -> (result, grid)

Correlate, and return the search grid alongside the result.

The same computation as autorift, which discards the grid. The result is indexed by grid point and only the grid holds the pixel position of each point, so mapping a displacement to a map coordinate needs it. The DimensionalData and Rasters extensions call this method. Takes the same keywords as the matrix form of autorift.

AutoRIFT.ondisk Function
julia
AutoRIFT.ondisk(a::AbstractArray) -> Bool

Whether reading an element of a costs I/O.

false for any array the core knows about. AutoRIFTDiskArraysExt returns true for a DiskArrays.AbstractDiskArray (chunked backends such as Zarr, NetCDF and HDF5) and AutoRIFTRastersExt for a file-backed Raster. autorift throws for such input on the unblocked path, which would read it one pixel at a time; pass process_block_size.

Add a method for a disk-backed type that neither extension recognizes. A wrapper needs its own method even when what it wraps is recognized.

AutoRIFT.halo Function
julia
AutoRIFT.halo(grid::PointSet, p::Params, imagesize) -> Extent

Pixels a block must read beyond what it writes, as an AutoRIFT.Extent.

The sum of the correlation reach (chip/2 + radius + ceil(abs(prior)) plus 2 pixels of slack) and the preprocessing filter's reach, each at its maximum over the run. The reach is evaluated at the coarsest level, not at grid as supplied, because a level sets its own chip size and floors the radii (see AutoRIFT._worst_level_points).

The filter term comes from AutoRIFT.filter_reach, not from filter_width ÷ 2: Wallis applies two chained window passes and so reaches twice its half-width.

The outlier filter is not included. It runs on the assembled field rather than per block, because its reach compounds past what a halo can absorb.

Throws ArgumentError for a preprocessing method with no finite reach, since no halo makes such a filter blockwise-reproducible.

source
julia
AutoRIFT.halo(p::Params) -> Extent

The halo for a grid AutoRIFT.gridpoints would build from p, without building it.

Every point of such a grid has the same chip size and radius, so the maxima are the values in p, with radii floored at min_search_radius as AutoRIFT.sanitize! floors them. Building a grid to obtain the halo costs 550 MiB and 50 ms on a Landsat-sized scene. For a caller-supplied PointSet, where per-point radii and priors may vary, use the grid form.

AutoRIFT.block_size_for Function
julia
AutoRIFT.block_size_for(grid::PointSet{2}, p::Params, imagesize; kw...) -> Extent
AutoRIFT.block_size_for(p::Params, imagesize; kw...) -> Extent

A process_block_size for this configuration: AutoRIFT.BLOCK_HALO_MULTIPLE (1) times the halo in each axis, at least AutoRIFT.BLOCK_FLOOR (1024) pixels, clamped to the scene. This is the smallest block the halo permits, with the floor preventing a tiny block when the halo is narrow.

Keywords: chunk, the (rows, cols) of the storage's own chunk grid, to which the size is rounded up, and floor_pixels, a further lower bound.

Blocks are the unit of threaded work, and each reads a fixed-width halo around itself, so both small and large blocks cost time. A block that is too small reads mostly halo: on the golden S1B case (halo 684x256), a 768x320 block has a read amplification of 7.23x and a higher peak memory than 1024 (3.24 GiB against 3.01). A block that is too large holds too much memory and too much work to balance across threads: at 2048 the buffers reach 10.32 GiB, and on NISAR L1 at 6144 px one block holds 19.8% of the granule, so twelve threads deliver the work of five.

The rule is fitted to a sweep of all 22 golden cases (tools/golden/block_optimum.jl), counting only block sizes that reproduce the untiled result. The per-case optima range from 128 px to 6144 px, so the size is expressed relative to the halo. The objective is wall clock subject to peak memory fitting 16 GiB. Minimizing peak instead costs 1.11x the runtime over the golden set (up to 2.02x on one Sentinel-1 case) to save about a gigabyte, and no rule tried peaks above 13.22 GiB over the harness floor (the shipped rule: 8.72 GiB). Relative to the best size per case, the multiple of 1 measures 0.99x on the two NISAR cases (83% of the set's wall clock), against 1.33x at 2 and 1.53x at 3. The 1024 floor measures 1.05x on the other twenty cases, against 1.08x at 768, 1.15x at 512, 1.10x at 2048, and 1.25x at 4096. The worst single case is 1.47x, on one that runs in 1.6 s.

The Params-only method assumes the grid AutoRIFT.gridpoints would build (uniform radii, axis-aligned, p.grid_spacing apart), as AutoRIFT.halo(p) does.

AutoRIFT.warm_plans! Function
julia
warm_plans!(sizes; complex = false)

Create the plans for sizes, an iterable of (ny, nx), on the calling task before any parallel work starts. Otherwise every task would contend on the planner lock at its first point. Called once per pass.

persist writes the FFTW wisdom measured here when the call finishes. Pass false from a caller that warms many sizes in sequence and persists on its own schedule, since FFTW's export rewrites the whole accumulated file.

complex selects the complex-to-complex pair that Coherence executes instead of the real-to-complex pair. It must match the measure the pass runs: the wrong kind pays full planning (hundreds of milliseconds per size, cold) for a plan that is never executed, and leaves the executed plans to be created inside a worker task.

AutoRIFT.precompute_fftw_wisdom Function
julia
precompute_fftw_wisdom(p::Params; max_search_radius) -> Int

Measure and persist the FFTW plans p can reach at any search radius up to max_search_radius, and return how many distinct transform sizes were planned.

A plan is measured on first use and persisted by AutoRIFT.fftw_wisdom_path. A process that finds wisdom on disk starts warm, and one that does not pays planning for every size its grid reaches. This function plans the whole reachable set up front, so the first job on a machine is as fast as later ones.

A point is correlated at its radius rounded up to a rung of the AutoRIFT._radius_bucket ladder, and the rungs are fixed rather than derived from the data. A larger time separation changes which rungs are reached but not what they are, so one precomputation covers every pair up to max_search_radius, the widest radius the deployment can produce. It is required because no default is right for every sensor. Throws ArgumentError if it is less than 1.

The pass maximum is not covered: _radius_bucket returns it verbatim for a radius at or above it, and it is a property of the grid rather than of the ladder. Sizes involving it are measured on first use, which is 10 to 15% of the sizes a real optical pair reaches.

Planning takes 116 to 347 ms per size for an optical pair and 8.2 s at the widest size of a NISAR pair with an 8 km search, so a few hundred sizes take minutes and a few thousand tens of minutes, once per machine type.

Progress is logged at most every progress_interval seconds (default 10), and wisdom is saved at the same time, so an interrupted run can be resumed by running it again.

source
AutoRIFT.fftw_wisdom_path Function
julia
AutoRIFT.fftw_wisdom_path() -> String or nothing

Path to this machine's FFTW wisdom file, or nothing if no directory is available to hold it.

The file name carries the CPU model (or the LLVM core name when the model is unknown) and the FFTW version, because wisdom is portable across neither. A directory may hold one file per machine type, and each process reads only its own.

The directory is a scratch space inside the Julia depot, so the first run on a machine measures its plans and later runs read them. Set AUTORIFT_FFTW_WISDOM_DIR to use another directory, for a deployment whose filesystem is discarded between jobs (for example shared storage). Writes are safe from several processes at once; see AutoRIFT.save_fftw_wisdom!.
